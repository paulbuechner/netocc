# netocc-vtk

NetOcc.Vtk: OCCT's TKIVtk (`IVtk`, `IVtkOCC`, `IVtkVTK`, `IVtkTools`) on NetOcc and NetVtk, OCCT shapes in VTK scenes. Generated by netocc-gen (`../netocc-generator/config/vtk.yaml`), built on netocc-core's OCCT and its build.py (imported as a module). Monorepo rules: `../CLAUDE.md`; NetVtk's side: `../../netvtk/netvtk-core/CLAUDE.md` (its interop file).

## Commands

```bash
# OCCT with TKIVtk, VTK from NetVtk's vcpkg registry (netocc-core's vcpkg.json and vcpkg-configuration.json)
(cd ../netocc-core && python build.py occt --triplet x64-windows && python build.py generate && python build.py native --triplet x64-windows)

# the modules: netocc-gen with NetVtk's SWIG files (python build.py netvtk prints the restored package's swig/), in an MSVC
# environment (libclang needs its headers)
dotnet run --project ../netocc-generator/src/NetOcc.Generator -c Release -- generate --occt-src <OCCT source> \
  --occt-include <prefix>/include/opencascade --core ../netocc-vtk --config config/vtk.yaml --netvtk <NetVtk's swig/> [--check]

python build.py generate                        # SWIG -> build/generated (restores NetVtk first)
python build.py native --triplet x64-windows    # NetOccVtk + TKIVtk -> artifacts/runtimes/<rid>/native
python build.py test --arch x64                 # net10.0, net8.0, net48 (also --arch x86); --no-rendering without OpenGL; --arch on Windows only
python build.py pack --rids win-x64,win-x86     # NetOcc.Vtk + NetOcc.Vtk.runtime.<rid> (netocc-core's pack first: NetOcc)
python build.py test-package --arch x64
dotnet build demo/NetOcc.Vtk.Viewer.Wpf -c Release   # the demo; run it and ask the user to look
```

**NetVtk: nuget.org, or local packs through `local-dev.props`.** Without it, every solution and `build.py` take `NetVtk.props`'s release from nuget.org (CI). `local-dev.props` (git-ignored, a copy of `local-dev.props.template`) sets `LocalNetVtkPackagesPath`, a netvtk checkout's `netvtk-core/artifacts/packages` (its `build.py pack`): `Directory.Build.props` restores from there at the version its `NetVtk.version.props` names, and fails without a pack; `build.py` reads it through MSBuild (`dotnet msbuild -getProperty`). Day-to-day work is local; nuget.org is the release CI's. A pack records a local NetVtk's folder in `NetOcc.Vtk.version.props` (`NetVtkPackageSource`), which the PackageTests and `samples-vtk` restore from. `NetOcc.Vtk.slnx` is the solution; `NetOcc.Vtk.local-dev.slnx` adds the local-dev files and NetVtk's interop typemaps, and is the template for a git-ignored personal `NetOcc.Vtk.<user>.slnx`. Locally, vcpkg fetches NetVtk's registry from a sibling checkout before it's on GitHub: `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=url.<netvtk checkout>.insteadOf GIT_CONFIG_VALUE_0=https://github.com/paulbuechner/netvtk`.

**Versions:** NetOcc.Vtk depends on the NetOcc netocc-core packed (`>=` its `NetOcc.version.props`). CI and releases pass that version (`--version`); a local pack gets its own `<OCCT>.<revision>-local.<time>`, its runtime packages too: NuGet keeps the first copy of a version it extracted. `NetOcc.Vtk.csproj` treats `Version` as local (`TreatAsLocalProperty`): `build.py pack` passes NetOcc's as `Version`, which reaches the NetOcc project reference (the dependency), and NetOcc.Vtk's as `NetOccVtkVersion`, then checks the nuspec's NetOcc, NetVtk and runtime dependencies.

## One VTK

- **The build:** netocc-core's opencascade[vtk] takes `vtk` from NetVtk's git registry (`vcpkg-configuration.json`: `packages: [vtk]`, the baseline a NetVtk release's commit), `vcpkg.json` asks for NetVtk's VTK features (`cgns`, `exodus`, `volume`; `opengl` comes with OCCT's), and netocc's triplets are copies of NetVtk's, byte for byte: vcpkg's ABI hash for VTK is the same in both repositories, and either's binary cache restores the other's build (verified 2026-10-12: win-x64, win-x86, linux-x64). `NetVtk.props` names the NetVtk release of that commit, `vcpkg.json`'s `vtk` override its VTK version and port-version: move all three together.
- **At run time** VTK's libraries are NetVtk.runtime's; NetOcc.Vtk.runtime holds NetOccVtk and TKIVtk only, NetOcc.runtime OCCT's others. `NativeLibraries` (module initializer) has NetVtk load VTK first (`vtkVersion.GetVTKVersion()`), then resolves NetOccVtk through NetOcc's loader (`NativeLibraryLoader.ResolveFor`); the OS loader finds VTK loaded; then `Vtk.VtkBuild.Require` checks the VTK build TKIVtk was compiled against (`extras/IVtk.i`'s `%netvtk_build`, NetVtk's `vtkNetVtkBuild.h`) against the one NetVtk carries, and throws where they differ.
- **Linux and macOS tests** build without a RID: with one (`--arch`), NuGet flattens NetVtk's VTK libraries into the output, while the project puts NetOccVtk into `runtimes/<rid>/native`, where its `$ORIGIN` finds no VTK (on Windows NetVtk has loaded every VTK DLL by name first). Apps keep them together either way.
- **win-x86:** OCCT's `IVtk_Types.hxx` refuses 64-bit VTK ids on 32-bit Windows; netocc's opencascade overlay port drops that guard (`0007-ivtk-64-bit-ids-on-32-bit-windows.patch`): TKIVtk handles its ids alike on 32 and 64 bits.

## Wrapper contract

- **NetOcc's types:** the modules `%import` NetOcc's (`../netocc-core/src/SWIG_files/wrapper`, its common typemap library); NetOcc grants `InternalsVisibleTo("NetOcc.Vtk")` for its proxies' pointers and constructors and the typemaps' helpers.
- **NetVtk's types:** through NetVtk's `swig/interop/NetVtkInterop.i`, never its typemap library (`%netvtk_object(T)`: `NativePointer` in, `FromNativePointer` out). VTK classes of TKIVtk (`IVtkTools_ShapeDataSource : vtkPolyDataAlgorithm`) are `%netvtk_derived(T, CSBase)`: their proxies derive from NetVtk's (`protected internal` pointer constructors), which hold the reference; `%netvtk_new(T)` is their C# constructor.
- **netocc-gen's VTK rules** (`config/vtk.yaml`): NetVtk's VTK objects come from its `wrapper/*.i` (`%vtk_object`, `--netvtk`); `library: NetOccVtk`; `import:` NetOcc's modules; `fixed_long_long: true` (IVtk_IdType is vtkIdType, `long long` everywhere: the picked ids' `NCollection_List<long long>`); `skips:` beside this folder (netocc-documentation's skipped-members page reads netocc-gen's own).
- **Picking:** `IVtkTools_ShapeObject.SetShapeSource(source, actor)` registers a shape's actor; `IVtkTools_ShapePicker` (renderer, selection mode, `Pick(x, y, 0)`) gives `GetPickedShapesIds()` and `GetPickedSubShapesIds(id)`, sub-shapes by `IVtkOCC_Shape.GetSubShape(id)`.
- **Highlight:** `IVtkTools_SubPolyDataFilter` passes the picked ids' cells; drawn by another shader over the same faces, they z-fight on screen. The demo moves the highlight actor toward the camera by 1e-4 of the camera's distance on the renderer's `StartEvent`. Not VTK's coincident-topology offsets: they write `gl_FragDepth`, which multisampling compares per sample (half the highlight loses), and without multisampling the edges break up into dashes.
